## 1. Why This Topic Exists

DNS translates human-readable domain names into IP addresses — the very first step of nearly every network request. Understanding its hierarchical design and caching behavior explains real production concerns like migration planning and geo-routing.

---

## 2. Core Concepts

### Why hierarchical, not one giant server

A single global DNS server would fail in three ways:
```
1. Scale        → billions of domains, trillions of lookups/day
2. Availability → one server = single point of failure for the entire internet
3. Management   → domain owners need control of their OWN records without
                   needing a central authority's permission
```

**The fix: delegate authority in layers**
```
Root Server         → knows WHICH server handles .com, .org, .in, etc.
TLD Server (.com)    → knows WHICH server is authoritative for google.com
Authoritative Server → owned by Google; has the real IP records
```

This is the same pattern as database sharding (Topic 005) — distribute responsibility instead of centralizing it.

### Resolution Flow
```
"google.com?" → Resolver → Root ("ask .com TLD server")
                         → TLD  ("ask Google's authoritative server")
                         → Authoritative ("142.250.183.100")
```

### Caching via TTL

If every lookup walked the full chain, DNS would be slow. Records are cached per **TTL (Time To Live)**:
```
DNS Record: google.com → 142.250.183.100, TTL = 300 seconds
Repeat lookups within 300s skip the entire chain — instant cached answer.
```

**Tradeoff:** longer TTL = faster/cheaper lookups but slower propagation of changes. Companies **lower TTL before a planned migration** so the change propagates quickly, then raise it back afterward for efficiency.

## Tech Decision Box: DNS Record Types

```
A record      → domain → IPv4 address
AAAA record   → domain → IPv6 address
CNAME record  → domain → another domain name (alias, e.g. www → root domain)
TTL           → how long a resolver may cache the record before re-checking
```

**GeoDNS:** returns different IPs for the same domain based on requester location — a cheap, simple form of geo-routing before any load balancer is involved.

---

## Real Engineering Examples

- **Migration playbook:** lower TTL before cutover, migrate, verify traffic shifted, raise TTL back
- **CDNs (Topic 018):** use DNS/GeoDNS to route users to the nearest edge server
- **DNS uses UDP** (Topic 008) — tiny, stateless queries, cheap to retry if lost

---

## Common Mistakes

| Mistake | Fix |
|---------|-----|
| Assuming one DNS server could theoretically know everything | Scale, availability, and management all require delegation into layers |
| Forgetting to lower TTL before a migration | Stale cached IPs cause users to hit the old server for the full TTL duration |

## Summary

- **DNS translates domain names to IP addresses** via a hierarchical chain: Root → TLD → Authoritative.
- **Hierarchy exists to solve scale, availability, and management** — the same "delegate responsibility" pattern as sharding.
- **TTL governs caching** — the core lever for balancing lookup speed against propagation speed.
- **Lower TTL before migrations**, raise it back after, to control how fast changes take effect.
- **GeoDNS** provides cheap, simple geo-routing before load balancers are involved.
