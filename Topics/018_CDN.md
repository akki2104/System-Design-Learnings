## 2. Core Concepts

### The fundamental problem — physics, not code

Cross-region latency is unavoidable — data can't travel faster than light. A round trip from India to a US origin server is ~150-200ms minimum, no matter how optimized the server code is. **A CDN's answer: don't make the request travel that far** — put copies of content physically closer to the user.

```
Without CDN:  User (India) ──────────very far──────────→ Origin (US)
With CDN:     User (India) ──short hop──→ Edge Server (Mumbai) [cached copy]
```

**A CDN is a geographically distributed network of edge servers that cache content close to users.** Each edge server is architecturally a **reverse proxy** (Topic 016) — sits in front of the origin; users don't know/care which edge served them. **GeoDNS** (Topic 009) is the routing mechanism — the same domain resolves to a different IP depending on the requester's location, pointing them to their nearest edge.

### Push vs Pull CDN

**Pull CDN (default, "lazy" model):**
```
1. User requests content → edge doesn't have it (cache miss) → fetches from origin
2. Edge caches it, THEN serves the user
3. Next user in that region gets an instant cache hit
```
Simple, self-managing. **Cost:** first request per region pays a full round-trip to origin (cold-cache penalty).

**Push CDN (proactive model):**
```
Origin explicitly uploads/publishes content to ALL edge servers ahead of time —
ready everywhere before any user requests it.
```
Used when zero cold-cache misses are acceptable — major launches, releases where millions of users hit simultaneously at go-live.

```
Pull → simpler, self-managing, first request per region is slow
Push → ready everywhere upfront, requires explicit distribution management
```

### Cache Invalidation — same problem as DNS TTL (Topic 009)

CDNs traditionally cache **static content** (images, video, JS/CSS, fonts). The hard part: how does the CDN know when origin content changes?

```
TTL-based expiry → cached content auto-expires after N seconds/hours
Explicit purge   → force-remove a specific cached object immediately via
                    the CDN's invalidation API — used when you can't wait
                    for TTL (e.g., a critical bug fix just shipped)
```

Same tradeoff as DNS TTL: short TTL = fresher content, more origin load; long TTL = less origin load, staler content longer, with explicit purge as the escape hatch for urgent cases.

## Tech Decision Box

```
Use a CDN when:
  - Global user base, cross-region latency matters
  - Serving static assets (images, video, JS/CSS)
  - Want to reduce origin server load

Pull CDN → default, less operational overhead, ok with slower first request
Push CDN → need guaranteed zero cold-cache misses (major launches, releases)

Short TTL → content changes often, freshness > origin load
Long TTL → content rarely changes, minimize origin hits + pair with
           explicit purge API for rare urgent updates
```

**Interview sentence:** "I'll put a CDN in front of static assets since most users are far from the origin region — this cuts latency and reduces origin load. I'll use a pull model since content changes frequently enough that push's upfront cost isn't worth it, paired with a moderate TTL and an explicit purge API for the rare cases needing instant updates."

## Common Mistakes

| Mistake | Fix |
|---------|-----|
| Thinking CDN latency gains come from server optimization | The gain is physical — reducing distance, not server-side speed |
| Waiting for TTL to expire after a critical content fix | Use the CDN's explicit purge/invalidation API immediately instead |

```
CDN = distributed network of edge servers (reverse proxies) caching
      content physically close to users — fixes latency that's PHYSICAL,
      not code-optimizable

ROUTING: GeoDNS (Topic 009) sends users to their nearest edge

PUSH vs PULL
─────────────────────────────────────────────────

CACHE INVALIDATION (same as DNS TTL, Topic 009)

```

## Summary

- **CDNs solve a physics problem** — speed-of-light distance latency — not a code problem.
- **Edge servers are reverse proxies** (Topic 016); **GeoDNS** (Topic 009) routes users to the nearest one.
- **Pull CDN** is the simple default; **Push CDN** guarantees zero cold-cache misses for major launches.
- **Cache invalidation mirrors DNS TTL tradeoffs**: TTL for steady-state freshness, explicit purge for urgent fixes.
